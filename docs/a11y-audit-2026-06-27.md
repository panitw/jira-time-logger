against the rendered DOM of each surface, scoped to WCAG 2.1 A + AA tags

**Result: zero Critical/Serious WCAG 2.1 AA violations across all surfaces.**

The hard gate filters to Critical/Serious severity. Moderate/Minor triage:
none outstanding — see `docs/a11y-deviations.md`.

`color-contrast` is disabled in the jsdom harness (axe needs a real paint
engine); it is verified manually below.

### Critical findings fixed during this audit

- **Options form controls missing accessible names** (`select-name`, `label`):
  `CycleField`, `ReminderTimeField`, `TargetHoursField`, `CatchAllProjectField`
  labels were not associated with their inputs/selects. → `htmlFor`/`id` added.
- **`TicketPicker` invalid composite-widget structure**
  (`aria-required-children`): a `role="listbox"` cannot own focusable
  `<summary>` disclosure headers. → Re-modelled as a `tree`
  (`tree` → `treeitem` leaves; `group` bodies; `aria-expanded` summaries).

## 14-item UX Accessibility Review Checklist

| # | Item | Status | Notes |
|---|------|--------|-------|
| 1 | All interactive elements reachable via keyboard alone | PASS | Radix Tabs/Dialog manage focus; hand-rolled menus (`role="menu"/menuitem`) and the `TicketPicker` tree use roving real focus. The non-canonical Approve button is now `aria-disabled` + focusable (was native `disabled`, dropped from tab order) — Story 6.1 AC4. |
| 2 | All interactive elements show visible focus ring | PENDING HUMAN VERIFICATION | `focus-visible:ring-2 focus-visible:ring-accent focus-visible:ring-offset-2` wired on shared `ui/{button,input,tabs,dialog}` and per-component triggers (2px accent ring + 2px offset, instant) — verifiable in code. The visual confirmation in a real browser still needs a human pass. |
| 3 | All icon-only buttons have `aria-label` | PASS | Guest-rail dismiss (Story 7.11: hand-inlined lucide `X` icon, `aria-label="Dismiss for today"` — was a bare `✕` text glyph pre-7.11); matrix cell buttons own the accessible name; menu triggers labelled. Asserted in scan + unit tests. |
| 4 | All status colors paired with icon + text label | PASS | Matrix/Week cells pair each state color with a lucide icon + text via the shared day-status vocabulary (Story 7.6): `CircleCheck`/`ChartPie`/`Circle`/`Diamond`/`Minus` from `components/shared/DayStatusIndicator.tsx`, plus `RefreshCw` (matrix "needs re-approval", a different axis, untouched) and `EyeOff` (restricted visibility — was `Lock`, D-7.6-11); dirty = diagonal-stripe pattern, not color alone. |
| 5 | All design-token text/background pairs pass 4.5:1 | PENDING HUMAN VERIFICATION | axe cannot compute contrast in jsdom. The design tokens in `styles/globals.css` are intended to meet 4.5:1 (3:1 for ≥18px), but the contrast measurement against rendered output still needs a human DevTools pass. |
| 6 | No information conveyed by color alone | PARTIAL — code-verified; sim pending | Every cell that carries a status EXCEPTION (matrix `gap`/`restricted`, week totals row) pairs its colour with an icon + a visible text label via Story 7.6's shared `DayStatusIndicator`, and the cell's own verbal `aria-label` states the figure and the status in words too. The week grid's BODY cells additionally carry a background-wash tint as redundant reinforcement only — that tint alone is never the sole signal, because the same day's status is already carried with icon+label one row up, in the totals cell (Finding 20: an earlier draft of this row overclaimed "every state cell carries an icon + label", which is false for the tint-only body cells specifically). Restricted visibility renders an `EyeOff` glyph with a visible "hidden" label (was a decorative-only `Lock`, D-7.6-11) — verified in code/tests. The color-blindness simulation that confirms this end-to-end (row 12) is still PENDING HUMAN VERIFICATION. |
| 7 | All forms submit on Enter from any field | PASS | QuickLogForm, settings fields (blur/Enter commit), guest-rail quick-log (Enter handler, unchanged by Story 7.11), GapAcknowledgmentDialog. Covered by existing component tests. |
| 8 | All overlays dismiss on Esc | PASS | Radix Dialog/Popover handle Esc; hand-rolled menus and the guest-rail quick-log handle Escape. Esc is never the destructive path. Story 7.11 (D-7.11-46): Escape while a submit is in flight is now gated (`shouldReevaluateOnEscape`, `lib/banner-interactions.ts`) so it no longer drops the success confirmation — closes a Story 3.3 deferred item. |
| 9 | All dynamic updates announced via `aria-live` | PASS | Matrix `<tbody aria-live="polite">`; status/badge regions `polite`; errors `assertive` (guest-rail error/status slot `role="alert"`, `lib/banner-dom.ts`). Story 7.11: the same slot is now reused to announce the SUCCESS confirmation too ("Logged {N}h — Closing…"), not just errors — closing a gap where the pre-7.11 banner changed a button's label silently on success. |
| 10 | `prefers-reduced-motion: reduce` replaces animations | PASS | Global guard in `styles/globals.css` collapses all ≥100ms animations/transitions. `LoggedToday` slide-in is now explicitly `motion-safe:animate-slide-in` (was unconditional); `TicketPicker` skeletons now `motion-safe:animate-pulse`; guest-rail slide uses `matchMedia` reduced-motion (Story 7.11: motion is now ONE property, `transform` only — the rail's height never changes, so there is no longer a height transition to gate). |
| 11 | Screen reader announces popup/dialog open/close + tab navigation | PENDING HUMAN VERIFICATION | The Radix-managed focus + `aria-live` wiring is in place (code/test-verified), but the actual NVDA (Windows) + VoiceOver (macOS) listening pass has not been performed and must be done by a human. |
| 12 | Color-blindness simulation: all flows understandable | PENDING HUMAN VERIFICATION | Requires a human running DevTools "Emulate vision deficiencies" (Protanopia / Deuteranopia / Tritanopia / Achromatopsia). Not yet performed. (Icon + text + stripe redundancy is present in code — row 6.) |
| 13 | Browser zoom 200%: no layout breaks | PENDING HUMAN VERIFICATION | Requires a human at Chrome 200% zoom. Not yet performed. |
| 14 | High-contrast OS mode: focus indicators remain visible | PENDING HUMAN VERIFICATION | Requires a human with macOS "Increase contrast" / Windows High Contrast enabled. Not yet performed. |

**Overall: 7 automated/code-verified items PASS; 6 items PENDING HUMAN
VERIFICATION; 1 (row 6) PARTIAL (code-verified, sim pending).** The pending
items (rows 2, 5, 6, 11, 12, 13, 14) require a human at a real browser /
assistive-tech / OS-theme stack — jsdom and an automated agent cannot evaluate
real paint, layout, screen-reader output, or OS theme. The release gate is NOT
green until a human performs and signs off on these.

## Manual passes — PENDING HUMAN VERIFICATION (not yet performed)

These passes have NOT been executed by the implementation/review agent (no
real browser, screen reader, or OS theme available). The code-level wiring that
each pass exercises is in place and verified by the automated scan + unit
tests, but a human must execute and sign off on each before the gate is GREEN.

- **Keyboard-only (mouse unplugged)** across the 6 major flows: First-run OAuth
  connect → Today log → Week submit (with gap dialog) → Manager approve →
  Manager drill-down → Guest-rail contextual log (Story 7.11 rebuilt this last
  flow's surface — the 44px rail — but the flow itself is unchanged: click/
  Enter the contextual action, type hours, Enter to submit, Esc to close).
  (Roving focus, Enter-to-activate, Esc-to-close and the `TicketPicker` tree
  navigation are unit-tested; the end-to-end unplugged-mouse pass — INCLUDING
  against the rebuilt rail — is still pending a human. Two things Story 7.11
  could not verify here and must be checked in this pass: whether
  `document.body.style.paddingTop` actually pushes a real Jira page's content
  down without overlap — jsdom does no layout, and if Jira's own header is
  also `position:fixed` the push may not help (accepted risk, D-7.11-30) —
  and the two by-design non-AA-contrast boundaries (rail-vs-Jira 1.06:1,
  hairline 1.27:1) read as intended and not as a rendering glitch.)

  submit / Manager approve. The non-canonical Approve button's disabled reason
  is now associated via `aria-describedby` → a visually-hidden node (code- and
  test-verified), but the actual SR listening pass is pending.
- **Color-blindness / zoom / high-contrast OS mode:** checklist rows 5, 6, 12,
